# supabase/schema — the schema of record

## The gap this exists to close

As of **2026-09-07** (first measured 2026-09-01: 224 applied / 32 files / 192 missing):

| | count |
|---|---|
| migrations applied to the live database | **240** |
| migration files in `supabase/migrations/` | **45** |
| applied live but never written back | **195** |

A clean checkout of this repo **cannot reproduce the database it talks to.**
Migrations are being applied straight to production — three landed on 2026-09-01
alone (`dispute_clients_out_of_localstorage`, `referrals_allow_khan_strategies`,
`credit_intake_affiliate_ref`), and a fourth (`packages_price_columns`) landed
while this file was being written.

That is not a bug in anyone's process so much as a missing step: nothing pulls
the schema back down.

## What's here now

- **`live-ledger-2026-09-07.tsv`** — the exact contents of
  `supabase_migrations.schema_migrations`, 240 rows, `version<TAB>name`.
  This is the authoritative list of what has actually been applied. It is the
  reference for deciding which of the 32 local files are real and which are
  orphans. Complete and accurate as of the timestamp in the name.

- **`live-baseline-<date>.sql`** — the full schema dump. **Not yet generated**;
  see below.

- **`live-roles-<date>.sql`** — roles and grants. Also generated by the script.
  Worth having separately: this system's security model leans hard on
  `REVOKE`/`GRANT` hardening (there are a dozen migrations named
  `revoke_*`), and a schema-only dump does not carry any of it.

## Generating the baseline

```
.\scripts\backfill-schema.ps1        # Windows
./scripts/backfill-schema.sh         # macOS / Linux
```

It prompts for the database password with the input hidden, hands it straight to
`pg_dump` via the Supabase CLI, and never writes, logs, or echoes it. Get the
password from the Supabase dashboard under **Project Settings → Database →
Database password**.

Run it again after anything lands live, and canon stops drifting.

### Why a password is needed at all

The service-role key in `.env` is a PostgREST JWT — it authenticates to the API,
not to Postgres. `pg_dump` needs a real database credential. There is no way
around this short of a Supabase personal access token, which has the same
problem of being a secret that has to come from you.

## Turning the baseline into a real migration baseline

The dump above is a *reference* — it is never replayed automatically. To make it
the migration baseline so the CLI treats everything before it as done:

```
supabase migration new baseline
# paste live-baseline-<date>.sql into the new file
supabase migration repair --status applied <that version>
```

The `repair` step is the important one: it marks the baseline as already applied
so it is never run against production. Without it, a `db push` would try to
recreate 161 tables that already exist.

## Rules

- **Read the diff before committing.** This is the entire schema; a dump is not
  a thing to wave through.
- **Owner gate applies.** No blind push. Commit locally, review, then decide.
- **`public` only.** The `auth`, `storage`, `realtime` and `net` schemas belong
  to the Supabase platform. Recreating them collides with it on restore.
